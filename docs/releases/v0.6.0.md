# rvc v0.6.0 — Web3Signer HTTP remote-signing API and a normative structured-logging standard

**Release date:** 2026-07-12
**Target tag:** `v0.6.0` on the same commit for `bin/rvc`, `bin/rvc-signer`, and `bin/rvc-keygen`.

This release adds an **opt-in Web3Signer-compatible HTTP remote-signing API** to
`rvc-signer` (so third-party consensus-layer clients — Lighthouse, Prysm — can
use it as a remote signer over HTTPS, alongside the existing gRPC service) and
lands a **normative structured-logging standard**: canonical `rvc.`-free field
keys across the whole workspace, value-level secret redaction, an opt-in JSON
log profile, per-site log sampling, runtime log-level reload, and a fail-closed
gitleaks CI gate. All three binaries must be upgraded together.

> **Scope.** 83 commits on `develop` since `v0.5.0` (`v0.5.0..develop`). `develop`
> is built directly on top of the `v0.5.0` release commit, so everything below is
> new relative to a `v0.5.0`-class build. If you are upgrading from an older
> release, also read the prior `docs/releases/vX.Y.Z.md` files and apply their
> operator actions.

## Breaking changes for operators

### Every `rvc.`-prefixed log field/span name is gone (`e2f2b66`, `6dfdadb`, `ea4f440`, `eb93113`, `53e557e`, `9cd4415`, `7b6f589`, `dd8bac5`, `13c6666`, `d9509cf`, `eddf139`, `e9d35a9`, `9395649`, and others)

The logging standard replaces the legacy `rvc.`-namespaced tracing keys with a
canonical registry (`crypto::logging::fields`) across every crate — e.g.
`rvc.slot` → `slot`, `rvc.secret_provider.*` → canonical equivalents. A standing
CI gate (`no_rvc_prefix.rs`) now fails the build if an `rvc.`-prefixed key
reappears in production code, so this is enforced permanently, not a one-time
cleanup.

**Action required if you have log-based dashboards or alerts:** anything
querying on an `rvc.`-prefixed field (Grafana/Loki/Datadog queries, log-based
alert rules, saved searches) will stop matching after upgrade. Update those
queries to the new bare field names (`slot`, `bn_url`, etc.) before or
immediately after rolling this out. See `plan/logging/STANDARD.md` for the full
field registry and `plan/logging/OPERATOR_GUIDE.md` for the reading guide.

### Slashing/duty log fields tightened and some spans demoted to `debug` (`1eba355`, `e9d35a9`, `eddf139`, `9395649`)

Alongside the key normalization, several previously-`info`/duplicate log lines
were demoted (slashing decisions now log once, at `debug`, instead of twice at
`error`; duty-tracker spans/cache lines moved to `debug`). If your alerting
keys off log *volume* or a specific level for these paths, re-verify it against
the new levels — see `plan/logging/OPERATOR_GUIDE.md` for the level taxonomy.

### Sensitive log values are now redacted/truncated by default (`aebeb41`, `2ee080b`, `ac150be`)

Signing roots, domains, remote pubkeys, and beacon/BN endpoint credentials are
now truncated or redacted at the value level before they reach any log sink
(console, file, JSON, OTLP) — e.g. a full 32-byte root now logs as
`0x0001020304...1c1d1e1f` rather than the raw hex, and `user:pass@host` URLs log
as `***:***@host`. This is a **strict reduction** in log content, not a format
change to existing fields; if you previously scraped a full root/pubkey/URL out
of logs for tooling, switch that tooling to the structured (non-log) source
(metrics, the gRPC/HTTP API, or the slashing DB) instead.

### No changes to existing config defaults, ports, or CLI flags

Everything above is additive or internal-only. The two genuinely new *opt-in*
surfaces (`[signer.http]` and the logging profile flags) are covered below and
default to their v0.5.0 behavior (HTTP API off, console pretty-printed
logging, no sampling, no runtime reload).

## New: Web3Signer-compatible HTTP remote-signing API (`rvc-signer`)

`rvc-signer` can now additionally serve the community **Ethereum Remote
Signing API** (`ethereum/remote-signing-api` v1.3.0, the "Web3Signer" HTTP/JSON
API) so Lighthouse and Prysm can use it as a remote signer. It is **additive**:
the existing gRPC service stays default-on and unchanged; the HTTP API is
**opt-in** and off by default.

> ⚠️ **Never expose this API to the public internet.** It has no
> application-layer authentication beyond TLS (and, in mTLS mode, the client
> certificate) and signs validator messages. Bind it to a private network /
> loopback behind firewall rules that permit only your validator client(s).

### Enabling it

```toml
[signer.http]
enabled        = true                 # opt-in; default false
listen_address = "127.0.0.1:9000"     # default 127.0.0.1:9000 (loopback, bindable, secure by default)
tls_mode       = "mtls"               # "mtls" (default) | "server-tls-only"
tls_cert       = "/etc/rvc/http-server.pem"
tls_key        = "/etc/rvc/http-server.key"
tls_ca_cert    = "/etc/rvc/ca.pem"    # required in BOTH modes
```

or the matching `--http-enabled` / `--http-listen-address` / `--http-tls-mode` /
`--http-tls-cert` / `--http-tls-key` / `--http-tls-ca-cert` CLI flags
(CLI > file > default precedence, same as the rest of `rvc-signer`'s config).
HTTP TLS material is independent of the gRPC listener's — you can run gRPC
with mTLS and HTTP with server-TLS-only, or any combination. Full setup
recipes (Lighthouse mTLS, Prysm server-TLS-only, SAN cert generation) are in
`plan/logging/OPERATOR_GUIDE.md` and `docs/web3signer-http-api.md`.

### Endpoints and coverage

- `GET /upcheck`, `GET /api/v1/eth2/publicKeys`, `POST /sign/{identifier}`.
- Every Web3Signer P0 sign type is dispatched: `BLOCK_V2`, `ATTESTATION`,
  `AGGREGATE_AND_PROOF` (+ Electra `AGGREGATE_AND_PROOF_V2`),
  `SYNC_COMMITTEE_SELECTION_PROOF`, `VALIDATOR_REGISTRATION`,
  `VOLUNTARY_EXIT`, `RANDAO_REVEAL`, `AGGREGATION_SLOT`, plus the base
  sync-committee sign arms — an all-types completeness gate pins this.
- Requests share the **same fail-closed `SigningGate`** as gRPC, so a
  double-vote/double-block over HTTP is rejected exactly as it would be over
  gRPC (`412`), proven by a real-gate cross-transport test.
- Server-side signing-root computation, `Accept`-header response shaping,
  `SigningGateError` → HTTP status mapping, a 1 MiB request-body cap (`413`
  over limit), and 404 pre-checks for unknown identifiers.
- HTTPS via `tokio-rustls` + `hyper`; audit CN is derived from the TLS peer
  certificate (server-TLS-only mode falls back to a documented default CN —
  it is an audit label only, never an authorization/slashing gate).
- Every sign request is audit-logged and instrumented on the existing shared
  `:9101` metrics registry.

## New: normative structured-logging standard

A workspace-wide logging initiative (tracked at `plan/logging/`) landed six
standing, fail-closed CI gates and three new opt-in operator knobs.

### Canonical fields, correlation, and redaction

- **Canonical field registry** (`crypto::logging::fields` + `Duty` enum):
  every crate's spans/events now key on the same field names workspace-wide
  (`slot`, `bn_url`, `pubkey`, …), with the `no_rvc_prefix` and
  `field_name_conformance` (Gate 5, now **blocking**) CI gates enforcing it
  permanently on a curated 16-event hot-path set.
- **Zero-alloc value wrappers**: `TruncatedRoot` / truncated-pubkey / redacted-URL
  types produce already-redacted strings before they're ever recorded, so
  redaction can't be bypassed by switching output format (proven for the new
  JSON profile too).
- **Correlation**: request-id and span-record helpers, plus an inbound W3C
  trace-context extractor in `rvc-telemetry`, so a duty's trace continues
  across the `rvc` → `rvc-signer` `:9000` sign boundary and through
  `produce_block_v3`.
- **`rvc-telemetry` pinned as a leaf sink**: an architecture-tests gate locks
  the new dependency edge so nothing downstream of telemetry can re-import
  application crates.

### Three new opt-in operator knobs

- **JSON log output** (`29d4f18`): `--log-format json` / `RVC_LOG_FORMAT=json`
  (both binaries, default `pretty`) flattens event fields plus the current
  span into top-level JSON keys for log-aggregation backends. Governs only
  the console layer — OTLP, the trace sampler, and the file appender are
  unaffected. Redaction is value-level, so JSON output is not a redaction
  bypass.
- **Runtime log-level reload** (`1c56c58`): `--enable-log-reload` (off by
  default) wraps the env filter in `tracing_subscriber::reload::Layer` and
  installs a SIGHUP handler that re-reads `RUST_LOG` and swaps the active
  filter with no restart. Disabled by default; the default path stays
  zero-allocation.
- **Per-site log sampling** (`3c8aeef`): `crypto::logging::should_log_sampled`,
  a dependency-light 1-in-N sampler applied to the highest-volume trace site
  (`rvc-signer`'s per-validator-per-slot attestation-stage trace). Sits behind
  an `enabled!(TRACE)` guard, so a disabled site never pays the sampling cost.

### CI: fail-closed secret scanning (`0c958a2`)

A new `secret-scan` CI job runs `gitleaks` (version- and SHA256-pinned) two
ways: (a) over the source tree with a path-only allow-list plus an exact
`file:rule:line`-fingerprinted baseline of published test vectors, and (b)
over a trace-level log sample emitted through the redaction primitives
(`crates/crypto/examples/log_sample.rs`), cross-checked by an explicit
content assertion that raw secrets are absent and redacted forms are present
— catching regressions gitleaks' entropy heuristics would miss (e.g. a
low-entropy password).

### `rvc-keygen` operator logging

`rvc-keygen` gained an operator logging breadth pass with mnemonic redaction,
and `rvc`'s per-slot loop gained a once-per-slot `info` heartbeat
(`crates/timing`) so "is it alive" is answerable from the default log level
alone.

## Upgrade path from v0.5.0

1. Stop `rvc`, `rvc-signer`, and any `rvc-keygen` jobs.
2. Replace all three binaries from the same `v0.6.0` build — they must be
   upgraded together.
3. **Log-based dashboards/alerts:** update any query keyed on an
   `rvc.`-prefixed field (e.g. `rvc.slot`) to the new bare canonical field
   name (`slot`) before or immediately after rollout — see the breaking-change
   section above and `plan/logging/STANDARD.md` for the full field list.
4. **HTTP remote-signing API (optional):** if you want Lighthouse/Prysm to use
   `rvc-signer` as a Web3Signer-compatible remote signer over HTTPS, add a
   `[signer.http]` block (or `--http-*` flags) with TLS material and, if
   binding off-loopback, a private-network address behind a firewall — **never
   a public interface**. See `docs/web3signer-http-api.md` and
   `plan/logging/OPERATOR_GUIDE.md` for worked per-client recipes. No action
   needed if you only use gRPC — it is unaffected and still default-on.
5. **JSON logs / log sampling / runtime reload (optional):** all three are
   opt-in and default to v0.5.0 behavior; enable via `--log-format json`,
   the automatic per-site sampler (no flag — it's compiled into the hottest
   trace site), and `--enable-log-reload` respectively. See
   `plan/logging/OPERATOR_GUIDE.md`.
6. Restart `rvc-signer`, then `rvc`.

No slashing-DB schema change and no config-format break in this release; all
new config surfaces are additive and default to the prior behavior.
